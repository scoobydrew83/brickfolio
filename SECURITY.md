# Security policy

## Reporting a vulnerability

Please **don't open a public issue**. Use GitHub's **Report a vulnerability** button on the Security tab of this repository (private vulnerability reporting). You should hear back within a week.

## Deployment notes

- Without `AUTH_MODE=better-auth` the app has no login of its own. Its security depends on the auth mode matching how it's exposed:
  - `AUTH_MODE=none` is only safe when the port is reachable from the same machine (the default compose binds `127.0.0.1`).
  - `AUTH_MODE=tailscale` trusts the `Tailscale-User-Login` header. Only run it with `compose.tailscale.yml`, which makes the app listen on `127.0.0.1` inside the Tailscale container so no one can send that header directly.
  - `AUTH_MODE=cloudflare-access` verifies the Access JWT signature, issuer and audience on every request.
  - `AUTH_MODE=better-auth` is Brickfolio's own email + password sign-in ([Better Auth](https://www.better-auth.com)). Set a long random `BETTER_AUTH_SECRET`. The first account becomes an admin, so sign up right after deploying; sign-up is then closed unless `ALLOWED_USERS` or `BETTER_AUTH_OPEN_SIGNUP=1` opens it. Passwords are hashed with scrypt, or PBKDF2-SHA256 (100,000 iterations) on Cloudflare Workers. Reset links shown to an admin (no email set up) are secrets: send them privately; they expire after an hour and are never logged. Setting or resetting a password signs that person out everywhere.
  - Passkeys (WebAuthn, `@simplewebauthn/server`) are bound to `BETTER_AUTH_URL`'s hostname and origin; registration needs a recent session. Two-factor TOTP secrets and backup codes are stored encrypted with `BETTER_AUTH_SECRET` (rotating it without Better Auth's secret rotation makes them unreadable), the second step allows 5 tries per sign-in, and Better Auth rate-limits `/two-factor/*`. Password sign-in asks for the code; passkey, email-link and social sign-in don't. A passkey sign-in is refused, and every request checked, for people not in `ALLOWED_USERS` or with an unconfirmed address.
- Permissions (`ADMIN_USERS`, Settings → People): admins can do everything; everyone else sees only the collections they have a role in (viewer, editor, owner). Every REST route declares what it needs (`api(need, …)` in `lib/api.ts`), every server action too (`act(need, …)` in `app/actions.ts`), and collection checks happen on the server (`lib/service/permissions.ts`); hiding buttons is only a convenience. Reads are cut down to the caller's collections in the services. With `ADMIN_USERS` unset, everyone allowed in is an admin.
- Bans and acting as someone (Settings → People): only admins, never on themselves or an `ADMIN_USERS` admin, enforced in the server actions and in a gate in front of Better Auth's `/api/auth/admin/*` endpoints (which otherwise trust only `user.role`). A ban deletes the person's sessions and every new session is refused while it lasts (password, emailed link, passkey and social sign-in all create sessions in one place, which checks it); in every auth mode a banned person gets no rights at all, API tokens included. Acting as someone ("impersonation") uses a session of theirs marked with the admin's id that lasts at most an hour: it has only that person's rights (never an admin's, so admin pages and actions refuse), can't be stacked, can't target admins or people who couldn't sign in themselves, and a bar on every page shows it. The admin's own session is kept in a signed cookie and comes back on **Stop**. The server-only endpoint that starts it (`/brickfolio/impersonate`) has no HTTP route.
- API tokens (`bf_` and a random secret of at least 256 bits) are shown once and stored only as their SHA-256 hash (base64url), in Better Auth's apiKey table (`apikey`, looked up by an index on the hash). They act with the current permissions of the person who made them; tokens with no owner (from before permissions existed, or made with `AUTH_MODE=none`) act as an admin, and only admins can see and revoke them. A token can expire (30, 90 or 365 days); revoking one takes effect on the next request. The older `api_tokens` table, which held the same hashes in hex, is kept unchanged for rolling back. A token stops working when its owner is no longer in `ALLOWED_USERS`; a share link stops working when the person who made it is no longer an owner of its collection or an admin. Revoke unused tokens in Settings.
- The REST API refuses writes (POST, PATCH, DELETE) that rely on browser identity unless they come from the app's own site (`Origin` / `Sec-Fetch-Site`), and requires `Content-Type: application/json` (or `text/csv` for import). This stops other websites from making changes through your browser. Requests with an API token are exempt.
- With Cloudflare Access, keep the application's cookie setting at `SameSite=Lax` (the default) unless you have a reason to change it.
- Keep BrickLink keys and `CRON_SECRET` in `.env` or Wrangler secrets, never in the repository.
